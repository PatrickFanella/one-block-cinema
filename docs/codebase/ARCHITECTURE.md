# Architecture

## Current architecture

One-Block Cinema is currently a local-first SwiftUI app shell generated by Rork.

## Entry flow

1. `OneBlockCinemaApp` starts the app.
2. `ContentView` owns the main tab shell.
3. `FilmSessionViewModel` coordinates current session state.
4. Views advance through template/theme selection, prompts, import-first clip attachment, assembly, preview/export, and saved sessions.

## Creation flow

1. `HomeView` starts a session from a selected `FilmTheme`.
2. `PromptGenerator` creates a sequence of `ShotPrompt` values.
3. `ShotSequenceView` presents the prompts.
4. `CaptureView` imports library clips and attaches them to prompts for MVP.
5. `AssemblyView` shows the collected clips and edit options.
6. `PreviewExportView` builds an AVPlayer item from the same immutable `RenderPlan` used by `VideoExportService` for export/share.
7. `SessionStorage` persists saved sessions locally.

## State model

- `FilmSessionViewModel` is the app state hub.
- Session data is modeled by `FilmSession`, `FilmTemplate`, `ShotPrompt`, and `FilmClip`.
- Current persistence uses a GRDB SQLite project store plus relative app-support media paths, with idempotent legacy JSON/`UserDefaults` migration and recovery records.
- Future sync should preserve offline-first draft behavior and private-until-publish defaults.

## Service boundaries

- `TemplateRepository`, `ProjectRepository`, and `MediaStore` separate local creation state from feature views.
- `RenderService`, `AuthService`, `SyncService`, `CommunityService`, `CritiqueService`, and `Analytics` define provider-neutral integration seams.
- `SessionStorage` implements the local project/media repositories and a SQLite sync-operation outbox.
- Every queued mutation has a stable idempotency UUID. Failed work remains durable with an attempt count and retry deadline.
- Sync conflicts retain the server project as canonical and create a local-only, clearly labeled `Recovered Copy` from local edits.

## Integration boundaries

- Media import: iOS Photos/library APIs for MVP; real camera APIs are post-MVP.
- Video preview/export: AVFoundation composition and video-composition instructions normalize orientation into the template aspect ratio at a 1080p-class output size.
- Inactive backend foundation: native Supabase Auth tokens, Fastify/pg-boss, RLS-protected Postgres/Storage, challenge/community contracts, and an admin moderation console. No iOS client is connected yet.
- Future AI: critique/coach feedback after MVP.

## Known mismatch

The generated UI promises a richer camera/editor/export experience than currently exists. Treat implementation work as productization of a shell, not completion of an existing production app. Real in-app camera recording is explicitly post-MVP; MVP work should remove, disable, or label camera placeholders.
